## 1. 结论

Inkmark 已是一个**功能闭环、工程成熟、可分发**的跨平台 Markdown 桌面编辑器。

它当前最大的欠账**不是「缺功能」，而是「真机验收没做完」**——近几轮的高价值修复（暗色窗口配色、代码块复制、表格逐字输入、命令面板、���片资源链路的最后一公里）大多只做到「静态验证通过 + 单元测试全绿」，从未在真实窗口里被人看过一眼；Windows / Linux 两个平台则从头到尾没在真机跑过。

因此本轮规划的落点不是「加更多功能」，而是**先把「敢用」和「下得动」补齐**，再按价值排序做增量。

### 4.1 竞品调研校准出的四条硬约束（来自本仓真实代码，非偏好）

产品经理完成 Typora / Obsidian / VS Code / Sublime / Zed / MarkText / Zettlr / Bree / Markor / Slash 的横向调研后，**有四条约束来自本仓代码本身**，它们不是「设计口味」，而是会直接改变实现形态的硬边界：

| # | 约束 | 依据 | 后果 |
|---|---|---|---|
| **C1** | **同路径不得开第二个标签**（打开已打开文件 = 切到已有标签） | `snapshot.go:48-55` 的 docKey = `hex(sha1(filepath.Clean(absPath)))[:16]`；`ADR-005 §四` 的多文档升级路径正是 `docKey → dirty` 映射 | 同文件两个标签 = 同一 docKey 两份内存内容两份 dirty → **映射退化，ADR-005 的 dirty 单义不变量被破坏**。故这是**架构约束**，不是可选 UX |
| **C2** | **未落盘新文档的 docKey 需独立命名空间** | 同上；`ADR-005 §四` 明确提到「刚创建尚未落盘的文档」 | 如 `untitled:<uuid>`，**不得与路径派生规则混用**，否则新文档的 dirty 会与某个真实路径撞键 |
| **C3** | **键位真源是 `useShortcuts.js` 的 COMMANDS 表，不是 ADR-004** | `main.go:18-33` 记录原生菜单已于 2026-10-06 整体下线，键位真源随之迁移 | `docs/architecture/ADR-004-keybinding-map.md` 状态仍为 "Proposed"、全文基于**已删除的** `buildMenu()` 架构，其「⌘1/2/3 = 视图三态」假设**已过时**。**不得依据 ADR-004 设计键位** |
| **C4** | **⌘1..⌘9 已被标题占用；⌘W 不可占用** | `format.h1`~`format.h6` = ⌘1~⌘6，⌘⌥0 = 正文（实测 `verify-shortcuts.mjs`：62 条命令 / 50 项键位） | **无法沿用 VS Code / Obsidian / Sublime / Zed 的「⌘1..9 直跳第 N 个标签」惯例**。⌘T / ⌘⇧T 空闲可直接采用。⌘W 涉及 macOS 系统语义 + Wails 窗口行为，需专项裁决 |

### 4.3 脏标记形态的裁决

竞品分歧明显：VS Code 用常驻白点；**Obsidian 刻意不做**（持续自动保存，星号只闪不到 1 秒即无意义 —— 官方论坛结论）；MarkText 则有「未保存改动被静默丢弃」的未决 issue。

本仓裁决：**保留 per-tab 脏标记，沿用 ADR-005 语义不变，但必须区分两种状态**——
- **dirty**（内存 ≠ 磁盘）：因 800ms 自动保存，通常转瞬即逝 → 视觉须**克制**（低调小圆点，不抢焦点）；
- **error**（自动保存失败 / 只读目录 / 未落盘新文档）：**异常态**，标记必须与 dirty **明确可区分**。

理由：本仓标题栏**现在就有**红点（`HANDOFF §6 #6`），去掉是行为回退；而 800ms 自动保存已使 dirty 窗口极短，视觉克制即可解决「噪声」问题。

### 4.4 建议明确「暂缓 / 不做」

- **插件系统**：第一版全部功能内置；真出现扩展需求时再做，成本比进程隔离沙箱低一个数量级。
- **多文档并排**：与「单栏居中流式」的减法定位直接冲突，引入后需要重新设计布局与滚动同步（历史上双栏/分屏/滚动联动已整体下线过一次）。
- **拼写检查**：在明确「英文长文写作」是主力场景之前不投入。

#### 4.5.1 一次「自裁反转」的记录（值得留痕）

        ↓

**为什么 ② 必须排在 ③ 之前**：多标签页要往 `App.vue` 加 `useTabLifecycle` 装配与 `TabBar` / `TabSwitcher` 模板（合计 6 行），而它现在正好压在 150 行硬上限上（`contracts.test.mjs:920-934`，口径是**总行数**，比有效行更严）。**先重构、后加功能**，否则每次加功能都要在「破门禁」和「临时豁免」之间二选一 —— 后者会永久削弱门禁效力。

**P0 里还夹带了一笔不查就会踩雷的债**：`createEditor.js` 有效行 **257 / 阈值 260，只剩 3 行余量**。多标签页要往编辑器侧加扩展清单，不先抽出去必然破门禁。顺带把阈值下调（棘轮只许降不许升）—— 这笔债的发现价值高于多标签页本身。

**总工作量**（架构师估）：P0–P3 约 4–5 天、P4 约 2 天、P5 约 1 天、P6 约 0.5 天，合计 **7–9 个工作日**（单人）。

### 5.1 风险最高的三个点（自动化守不住 / 守得住 已标注）

| 风险 | 后果 | 自动化 |
|---|---|---|
| **切标签丢内容**（`session.state` 未回写 → 切回显示旧内容） | 静默丢稿 | **守得住**（真 EditorView 驱动，断言切回后 `view.state.doc` 是最新内容） |
