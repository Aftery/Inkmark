## C-1（高）未落盘且有改动：架构说 warn，AC-71 说 error

**位置**：架构 §4.9 四态表（`multi-tab-architecture.md:688-700`）vs 测试 AC-71（`multi-tab-test-plan.md:499`）、AC-69（`:497`）

**架构的四态表**：

| 状态 | 判据 | 形态 | token |
|---|---|---|---|
| 干净 | `!dirty && saveState !== 'error'` | 无标记 | — |
| dirty | `dirty && saveState !== 'error'` | 5px 实心圆点 | `var(--muted)` |
| **未落盘** | **`path === ''`** | `AppIcon name="circle-dot"` | `var(--warn)` |
| error | `saveState === 'error'` | `AppIcon name="circle-dot"` | `var(--danger)` |

**问题一：判据不互斥，且未规定跨维度能否并存。**
表中「未落盘」的判据是 `path === ''`，与「dirty」的判据 `dirty && saveState !== 'error'` **可以同时为真**。一个新建未落盘文档一旦有输入（`dirty = true`），按架构会**同时**出现 muted 圆点（dirty 维度）+ warn 图标（未落盘维度）两个标记。架构只规定了「error 与 dirty 不同时出现（error 优先）」，**没有规定「未落盘维度」与「dirty 维度」能否并存**。

**问题二：与 AC-71 直接矛盾。**
AC-71 要求：「标签未落盘（filePath 为空）**且**有未落盘改动 → 必须呈 **error** 态标记」，理由是它**永远无法自动保存**（`useDocumentState.js:136` 的 `markDirty` 只在 `filePath` 非空时调度自动保存）。按架构 it'll 是 warn 图标，按 AC-71 是 danger 图标 —— **同一状态两种颜色**。

**问题三：这不是边角状态，是 D-3 场景的必然结果。**
D-3 裁决为「未落盘标签创建时 dirty=false，一有输入即 dirty=true」后，「新建未落盘文档 + 输入文字」正是最常见的正常路径，而它恰好落在两套规格的冲突点上。

**建议裁决（PM 倾向）**：采用**二维判据**，把「未落盘」拆成两行，并把「未落盘且有改动」归入 error：

| 状态 | 判据 | 形态 | token |
|---|---|---|---|
| 干净 | `!dirty && saveState !== 'error' && path !== ''` | 无标记 | — |
| dirty | `path !== '' && dirty && saveState !== 'error'` | 5px 实心圆点 | 见 C-9 |
| 未落盘且**无**改动 | `path === '' && !dirty` | `circle-dot` | `var(--warn)` |
| **未落盘且有改动** | `path === '' && dirty` | `circle-dot` | `var(--danger)` |
| error | `saveState === 'error'` | `circle-dot` | `var(--danger)` |

理由：AC-71 的洞察是对的 —— **永远无法自动保存**的文档，其字只存在于内存里，这是异常态而不是提示态，用 danger 合理；而「未落盘且没内容」没有东西可丢，用 warn 提示即可。修正后四个状态互斥，AC-69/AC-71 无需改写，架构四态表也无需保留并存规则。

## C-2（高）架构「必含」的两项能力，测试计划无任何 AC

**证据**：测试计划全文检索「拖拽 / 右键菜单 / contextmenu / reorder」，命中 5 处，**全部**出现在 AC-61 与真机第 44 项的**条件句**里 —— 即「若侧栏提供『打开的文档』列表，则它必须与标签栏能力对等（右键菜单、中键关闭、拖拽重排三者缺一不可）」。**没有任何一条 AC 断言标签栏自身支持拖拽重排或右键菜单。**

**建议**：补两条 AC（形态建议，对齐测试计划既有风格）：
- 标签栏支持拖拽重排，且重排后**顺序被持久化**（重启后顺序不变）—— 后半句是它区别于「临时视觉操作」的关键。
- 标签栏标签支持右键菜单，且菜单项集合与中键关闭行为**不依赖浮层是否渲染**（与架构 §4.10 的降级设计同源）。

**注**：架构 §9.5 只登记了 MarkText #5614 一条负向用例，其余竞品负向用例在测试 §3.11（7 条）。§5.2 ⑪ 已写「架构 §9.5 + 本文 §3.11 取并集」，此口径正确。

## C-5（中高）「关到只剩一个标签」在架构侧完全没有落点

**位置**：测试 §2.1 D-2（`multi-tab-test-plan.md:217-223`）vs 架构全文

架构全文检索「最后一个标签 / last tab / 全部关闭 / closeAll / 空状态 / empty」→ **零命中**。架构 §0.3 的必含 8 项与明确不含 5 项里都没有它；§5 的切换时序只覆盖「切到另一个标签」；§4.5 `closeTab` 没有覆盖「关到零」这个边界。

**为什么这是缺口而不只是措辞差异**：测试 D-2 的 QA 倾向是「**保留（不关到零标签）**」，理由是零行为变更、净增复杂度。但这只是**测试侧的倾向**，架构侧从未拍板过「关到最后一个标签会发生什么」——架构目前既没有实现路径，也没有把它列为「明确不含」。

**PM 结论（并对我自己上一轮建议的修正）**：
我上一轮给 QA 提的是「关闭最后一个标签 → 应用保持运行 + 专用空状态组件（新建/打开两个入口）」。**我撤回「专用空状态组件」这一半**，改支持 QA 的 D-2 方案（保留一个空文档）。理由是硬约束：
- 架构 §4.11 写明 **App.vue 150 行门禁「当前实测 150，余量为 0」** —— 新增一个空状态组件 + 分支会直接破门禁（契约 5），且 App.vue 是装配层，塞视图不 合它 150 行的定位；
- QA 方案复用现状（`filePath === ''` 的空文档，`useFileOps.js:144-148`），**零新 UI、零新分支、零回归面**，且「无文件打开」今天就是这个状态，用户不需要学；
- 我原方案里「空状态提供新建/打开两个入口」这个诉求，现状标题栏本来就有（新建/打开按钮），不需要新组件。

**保留的一半**：**应用不得退出进程**。这条与「保留空文档」不冲突 —— 关闭最后一个标签后，编辑器停在空文档态，窗口仍在。退出只由显式动作触发（`⌘Q` / 菜单退出 / 标题栏 × 走既有 `CloseWindow(dirty)` + `OnBeforeClose` 守卫）。

**建议**：架构补一条（§0.3 必含或 §5.4 `closeTab` 的边界），并把「关到零标签 = 应用退出」显式排除。测试侧补 AC 覆盖：关到最后一个标签 → 断言窗口仍在 + 停在空文档态。

## C-6（中）AC-66 覆盖不住「一次按住之内」，而现有实现在 AC-66 下会全绿

**位置**：架构 §4.5 + §4.10（`multi-tab-architecture.md:579-590`、`:723-729`）vs 测试 AC-66（`multi-tab-test-plan.md:476`）

**架构现状**：
- §4.5：「MRU（最近访问顺序）：`useEditorSession` 维护 `mru = ref([])`… **每次激活把目标移到头部**」；
- §4.10：「`keydown` 重复触发 → 在 MRU 顺序里循环移动高亮项（这天然实现了『按住循环』）」。

两条组合的推论：MRU = `[C, B, A]` 时按住切换键，keydown1 切到 B → MRU 变 `[B, C, A]` → keydown2 切到 C → MRU 变 `[C, B, A]` → keydown3 又切回 B…
**结果是第三个标签 A 永远够不到，按住不放只在最近两个标签间抖动。**

**为什么测试计划拦不住**：AC-66 写的是「用『切换到上一个 / 下一个标签』命令**连按两次**，第二次必须回到『上一个访问过的标签』」。连按两次 = 两次独立调用，而 MRU 语义下这本来就该回到上一个 —— 上面那个实现在 AC-66 下**完全通过**。AC-66 测的是「独立调用之间的 MRU 语义」，架构出 bug 的是「**一次按住之内**的遍历语义」，**两者是同一段代码（keydown 重复触发）但判据只写了一半**。

**PM 结论（已同步架构师与 QA）**：单次按住（一个 keydown→keyup 周期内）必须使用**首次按下瞬间的 MRU 快照**，在快照内循环；下一次独立按住才重取快照。这与 Sublime 的 `Ctrl+Tab`、Zed 的 Tab Switcher 一致。
**判据要点**：断言「三个不同标签都被访问过」，**不要断言最终停在哪个**（落点取决于最后一次 keydown 时序，不稳定）。降级路径（浮层渲染异常时直接切换）必须使用同一份快照，否则降级反而更糟。

### C-10（中高）三档落点策略的等价变异是**系统性**的，不是一个场景的偶发

**位置**：测试 D-3 三策略表（`multi-tab-test-plan.md:239-249`）+ 架构 §4.5 `pickLandingSession`（`multi-tab-architecture.md:581-587`）

QA 已识别「A、B、C → 关 B」这一例中 `history` 与 `left_neighbour` 同为 A（等价变异）。**复核发现：这不是那一个场景的偶发，而是「关掉最右侧标签」时的必然结果。**

推导：若标签按 A、B、C 的顺序**打开**（显示序即访问序），MRU = [C, B, A]。关掉 C（活动标签）时：
- `history` → MRU 中第一个非 C = **B**
- `left_neighbour`（C 的左邻）= **B**
- `neighbour`（C 的右邻）→ 不存在

⇒ **history 与 left_neighbour 判据同时通过**。四标签同构：开 A、B、C、D 关 D → history = C = left_neighbour。

**根因**：当活动标签的 MRU 前驱恰好是它的左邻时，两策略同解。MRU 由**访问顺序**决定，显示序由**打开 / 拖拽顺序**决定 —— 只要构造「访问序 ≠ 显示序」，即可区分。

**可区分场景（三档互不相同）**：

| 项 | 设定 |
|---|---|
| 显示序（左→右） | A, B, C, D |
| **访问序（点击顺序）** | **D → B → A → C** |
| 推导 MRU | [C, A, B, D]，活动标签 = C |
| 关掉 C 后 | `history` → **A**（C 的前一个访问对象）<br>`neighbour`（右邻）→ **D**<br>`left_neighbour`（左邻）→ **B** |

三档互不相同，且 `history`（A）刻意选了一个「既不是左邻也不是右邻」的标签。

**测试写法要点（QA 落地时必须照做）**：该场景**必须靠「按指定顺序点击」构造 MRU，不能靠「按顺序打开」**。用「打开顺序」构造的话，MRU 必然退化成显示序的逆序，上表就退回前述等价变异。

### C-11（中）落点策略在「目标不存在」时的回退未定义；且缺少「关闭非激活标签」的规则

**位置**：架构 §4.5 + §5.4 `closeTab` vs 测试 D-3 三策略表

**问题一：回退未定义。** Zed 的语义是「Activate the right neighbour tab **if present**」（`https://zed.dev/docs/reference/all-settings`）—— 「if present」意味着不存在时要回退，但**回退到哪，两份文档都没写**。
而这不是边缘情况：**只剩 2 个标签时关掉右边那个，`neighbour`（右邻）就没有目标**。最常见的场景恰好落在这个空洞里。

**PM 建议（需 team-lead 拍板）**：**三档统一回退到 `history`**；`history` 自身无候选时（MRU 耗尽）回退到「显示序上第一个剩余标签」。
- 理由：只有一条回退规则，三档之间不产生新的等价变异。
- **已否决的备选**：`neighbour` 定义为「有右邻取右邻、否则取左邻」—— 这会让 `neighbour` 在 2 标签场景下 ≡ `left_neighbour`，**制造一个新的等价变异**，与 C-10 的治理目标相反。

**问题二：关闭「非激活标签」的行为没写。** 现两份文档只定义了「关闭后激活谁」，但没定义「关闭一个不是当前激活的标签时，当前激活标签该不该变」。**产品规则：不得变** —— 关掉一个后台标签不应把用户从当前文档拽走。这与 VS Code / Obsidian 一致。
这条与三档策略正交，需单独一条 AC（当前激活标签在关闭非激活标签前后**必须是同一个**）。

### 关于 C-9 的数值澄清（第二轮）

本轮按 `design-tokens.css` 的**实际**底色重算（标签栏位于界面外壳上，故对比度应**对 `--surface`** 算，而非对文档画布 `--bg`）：

| 主题 | `--meta` vs surface | `--danger` vs surface | meta/danger | `--muted` vs surface | muted/danger |
|---|---|---|---|---|---|
| 浅色 default | 3.11:1 | 5.55:1 | 1.78× | 4.78:1 | 1.16× |
| 暗色 柔黑 | 3.66:1 | 6.06:1 | 1.66× | 5.70:1 | 1.06× |
| paper 纸张 | **3.07:1** | 5.63:1 | 1.83× | 4.83:1 | 1.17× |

底色取值：`--bg` / `--surface` 浅色 `#FFFFFF` / `#F7F8FA`、暗色 `#14151A` / `#101116`、paper `#FAF7F1` / `#F3EEE5`（`design-tokens.css:35-36, 94-95, 154-155`）。

三点结论：
1. **QA 的数值正确**（3.11:1 / 5.55:1 正是对 `--surface` 算的结果），C-9 原报告里对 `--bg` 算的值已在本表更正；两者**倍数完全一致**（1.78× / 1.66×），说明相对亮度算法无分歧。
2. **`--meta` 在三主题下均 ≥ 3:1**，但 paper 主题 3.07:1 是绑定约束（仅高出 WCAG 非文本下限 0.07）。故 AC 的阈值**必须写明对 `--surface` 算**，且三主题都要过。
3. **`--muted` 与 `--danger` 的对比度差距只有 1.06~1.17 倍**（暗色主题几乎重合）—— 若 dirty 标记用 `--muted`，它在暗色下与 error 几乎无法靠对比度区分。C-9「统一到 `--meta`」的结论因此更强：**不是措辞问题，是可用性问题**。

## C-8（低）AC-56 的竞品来源与该 AC 讲的不是一回事

但 AC-56 的判据是「用路径的不同写法（`dir/../b.md` 与 `b.md`、`dir//b.md` 与 `dir/b.md`）打开同一文件，必须判为同一文档」，其来源列写的是「Obsidian 社区插件 issue #55：同文件两个标签只存了一个光标位置」。

## C-9（低，但实算结果与裁决意图相反）dirty 圆点用 `--muted` 与 AC-67 的 `--meta` 不是同一个 token

**位置**：架构 §4.9（`multi-tab-architecture.md:693`）vs 测试 AC-67（`multi-tab-test-plan.md:495`）与 §3.13 对比度实算表（`:503-506`）

- 架构写死：dirty 圆点 `background: var(--muted)`，并注明「低调、不抢焦点」。
- AC-67 写：标记的计算色**必须取自 `--meta` 级 token**，对标签底色对比度 **≥ 3:1**，且 **< `--danger` 级 token 的对比度**。

**实算（本轮 node 脚本，WCAG 相对亮度公式）**：

| 主题 | token | 值 | 对 bg | 对 surface |
|---|---|---|---|---|
| 浅色 | `--muted` | `#6B6E7A` | **5.08:1** | 5.08:1 |
| 浅色 | `--meta` | `#8A8D99` | **3.31:1** | 3.31:1 |
| 浅色 | `--danger` | `#B23B31` | 5.89:1 | 5.89:1 |
| 暗色 | `--muted` | `#8A8D99` | **5.21:1** | 4.87:1 |
| 暗色 | `--meta` | `#6A6D78` | **3.34:1** | 3.12:1 |
| 暗色 | `--danger` | `#DF7268` | 5.53:1 | 5.17:1 |

（token 值来自 `frontend/src/themes/tokens/design-tokens.css:38,48,62-63,97,104,118-119`；暗色底色按该文件暗色块的 `--bg` / `--surface` 取值。）

**三个问题**：
1. **两个 token 不是同一个，且在暗色下值互换**（浅色 muted 更暗、meta 更亮；暗色 muted 更亮、meta 更暗）。实现者按架构写 `--muted` 时，AC-67「取自 `--meta` 级 token」的字面判据不成立。
2. **测试计划 §3.13 的实算表算的是 `--meta`，从未算过 `--muted`** —— 架构实际指定的那个 token 的对比度在两份文档里都没有数据。AC-67 的阈值是对着另一个 token 验证的。
3. **实算显示架构的选择与 team-lead「视觉须克制」的裁决意图相反**：`--muted` 在两个主题下都比 `--meta` 显眼（浅色 5.08 vs 3.31，暗色 5.21 vs 3.34）。暗色主题下 `--muted` 是候选里较显眼的一档，与「低调小圆点、不得高对比」相反；而 `--meta`（3.31:1 / 3.34:1）恰好落在 WCAG 非文本 3:1 之上、又明显低于 danger，是 dirty 标记的正确档位。

**建议**：**统一到 `--meta`**，理由：(a) 符合「克制」裁决意图；(b) 两主题均满足 ≥3:1；(c) AC-67 的实算表已覆盖该 token，无需重算；(d) 与 `--danger` 的对比度差距在两主题下都更宽裕（浅色 3.31 vs 5.89、暗色 3.34 vs 5.53），AC-67 的「必须 < danger 对比度」判据不会像 `--muted` 那样只剩 0.32~0.81 倍的薄余量。
**同时**：AC-67 / AC-68 的措辞「`--meta` 级 token」「`--danger` / `--warn` 级 token」应改为**指名具体 token**，避免「级」被理解为「某一档里的任意 token」。
